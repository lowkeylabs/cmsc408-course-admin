Security - SQL Injection

SQL Injection - Introduction

SQL Injection: What is it?

  • A common security vulnerability in web and API applications.
  • Enabled by lazy or immature SQL coding practices.
  • Occurs when an attacker manipulates input to execute malicious SQL queries.
  • Common in older web and api applications

SQL Injection - Examples

The Problem: Unsanitized User Input

  • Web applications often take user input through forms or query strings.
  • If not properly validated and sanitized, user input can be used to alter SQL queries.

Example 1: Unauthorized Access

  • Scenario: Login Page
  • Vulnerable Code:
query = """
SELECT * FROM users 
WHERE username='{inputUsername}' 
AND password='{inputPassword}';"
"""
  • Attack: Input as inputUsername = ' OR '1'='1'--
  • Result: Successful login bypassing password.

SQL Injection - Examples

Example 2: Data Leakage

  • Scenario: Search Feature
  • Vulnerable Code:
query = """
SELECT * FROM products 
WHERE name LIKE '%{searchKeyword}%';
"""
  • Attack: Input as searchKeyword = ' UNION SELECT username, password FROM users--
  • Result: Returns user credentials alongside product data.

Example 3: Database Deletion

  • Scenario: Delete Account Feature
  • Vulnerable Code:
query = """
DELETE FROM users WHERE id={userID};
"""
  • Attack: Input as userID = '1; DROP TABLE users--
  • Result: Deletes the entire ‘users’ table.

SQL Injection - Mitigation

It’s pretty simple, NEVER build a query raw. Here are a few suggestions.

 

Solution 1: Prepared Statements

  • Parameterized queries that separate SQL code from user input.
  • Example (Python):
cursor.execute("""
SELECT * FROM users 
WHERE username = ? AND password = ?
""", (inputUsername, inputPassword))

Solution 2: Input Validation

  • Validate and sanitize user input.
  • Reject input that doesn’t meet expected criteria.
  • Examples:
    • Ensure email input is a valid email address.
    • Remove extra spaces from user names.
    • Remove comment “–” strings from query.
    • Remove semicolons “;” from inputs.

SQL Injection - Mitigation

Solution 3: Least Privilege Principle

  • Avoid using highly privileged accounts in application code.
    • Create a unique user for the web application,
    • Don’t use your developer account or other account.
  • Limit the web application user permissions in database.
    • Allow web app INSERT, UPDATE, and DELETE
    • Disallow web app DROP, CREATE, GRANT, others.

Solution 4: Web Application Firewalls (WAFs)

  • Implement a WAF to detect and block SQL injection attempts.
  • Regularly update and configure the WAF.

SQL Injection - Summary

Best practices

  1. Use prepared statements or parameterized queries.
  2. Implement input validation.
  3. Follow the least privilege principle.
  4. Use a Web Application Firewall (WAF).

Recap

  • SQL Injection is a serious security threat.
  • Prevention is essential through proper coding practices.
  • Stay updated on security best practices and vulnerabilities.

Example 1: Solution 1 - using aggregate functions

SQL Code

with by_all as (
  select sum(mfg) as total 
  from indicators
),
by_grp as (
  select grp, sum(mfg) as grp_tot 
  from indicators
  group by grp
)
select
  a.country,
  a.grp,
  a.mfg,
  b.total,
  c.grp_tot,
  round(1.0*a.mfg/b.total,2) as over_all,
  round(1.0*a.mfg/c.grp_tot,2) as over_grp
from 
  indicators a 
    join by_all b
    join by_grp c on (a.grp=c.grp)
order by 
  country

Example 1: Solution 2 - using Window functions

SQL Code

select
  country,
  grp,
  mfg,
  SUM(mfg) over () as total,
  SUM(mfg) over (PARTITION BY grp) as grp_tot,
  ROUND(
    1.0 * mfg / 
      SUM(mfg) over (),
  2) as over_all,
  ROUND(
    1.0 * mfg / 
      SUM(mfg) over (PARTITION BY grp)
  ,2) as over_grp
from 
  indicators 
order by 
  country

Example 1: Comparison of solutions

Solution 1 — Using Aggregate Functions + CTEs

  • Uses CTEs (by_all, by_grp) to pre-compute totals.
  • Performs aggregate calculations once, then joins results back to the base table.
  • Relies on GROUP BY inside the CTE for group totals.
  • Joins produce a flat table with totals duplicated for each row.
  • Clear separation of logic: compute → join → calculate percentages.
  • More familiar for students already comfortable with GROUP BY.

Solution 2 — Using Window Functions

  • Uses window aggregates (SUM() OVER) to compute totals directly in each row.
  • Eliminates the need for GROUP BY, CTEs, and joins.
  • Computes global total and group total using window partitions.
  • Allows per-row metrics (like percentages) without changing the row structure.
  • More concise and expressive: all logic kept in a single SELECT.
  • Ideal for analytics queries where rows must remain unaggregated.

Example 2: Solution 1 - Ranking using correlated subqueries

SQL Code

SELECT
a.country,
a.grp,
a.mfg,
-- Rank across the entire sample
(
  SELECT COUNT(*)
  FROM indicators x
  WHERE x.mfg > a.mfg
) + 1 AS rank_all,
-- Rank within each group
(
  SELECT COUNT(*)
  FROM indicators y
  WHERE y.grp = a.grp
  AND y.mfg > a.mfg
) + 1 AS rank_grp
FROM indicators a
ORDER BY country;

 

Result set

country grp mfg rank_all rank_grp
Brazil Moderate 55 6 2
China Moderate 68 5 1
Germany High 84 2 2
India Moderate 49 7 3
Japan High 79 3 3
Mexico Moderate 46 8 4
South Korea High 71 4 4
United States High 92 1 1

Example 2: Solution 2 - Ranking using window functions

SQL Code


SELECT
  country,
  grp,
  mfg,
  -- Rank across the entire sample
  RANK() OVER (
    ORDER BY mfg DESC
  ) AS rank_all,
  -- Rank within each group
  RANK() OVER (
    PARTITION BY grp
    ORDER BY mfg DESC
  ) AS rank_grp
FROM indicators
ORDER BY country;

 

Result set

country grp mfg rank_all rank_grp
Brazil Moderate 55 6 2
China Moderate 68 5 1
Germany High 84 2 2
India Moderate 49 7 3
Japan High 79 3 3
Mexico Moderate 46 8 4
South Korea High 71 4 4
United States High 92 1 1

Example 2: Comparison of solutions

Solution 1 — Correlated Subqueries

  • Uses correlated subqueries to compute ranks.
  • Rank = count of rows with higher mfg value + 1.
  • Needs two separate subqueries: one for overall rank, one for group rank.
  • Logic is explicit but more verbose and repetitive.
  • Runs on any SQL engine (maximum compatibility).
  • Good for understanding how ranking works behind the scenes.

Solution 2 — With Window Functions

  • Uses RANK() OVER for concise, declarative ranking.
  • rank_all computed with ORDER BY mfg DESC.
  • rank_grp computed with PARTITION BY grp.
  • No subqueries, no joins — logic stays inside a single SELECT.
  • More readable and maintainable.
  • Ideal for analytics workloads; modern SQL expresses ranking directly.

Window analytic functions

Window Analytic Functions

A window function performs a calculation across a set of related rows without collapsing them (unlike GROUP BY).

Window function syntax

A window is defined by three clauses:

<window_function>() OVER (
    PARTITION BY ...
    ORDER BY ...
    ROWS | RANGE ...
)
  • PARTITION BY = groups (like GROUP BY but output is not collapsed)
  • ORDER BY = defines row ordering inside each partition
  • ROWS / RANGE = defines a sliding window relative to each row

Window function example

SELECT
  country,
  population,
  sum(population) OVER 
  (ROWS BETWEEN 
     UNBOUNDED PRECEDING 
     AND UNBOUNDED FOLLOWING
   ) as TOTAL

Categories of Window Functions

Ranking Functions

  • ROW_NUMBER()
  • RANK()
  • DENSE_RANK()
  • NTILE(n)

Aggregate Window Functions

  • SUM() OVER
  • AVG() OVER
  • MIN() OVER
  • MAX() OVER
  • with frames like: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

Value Functions

  • LAG()
  • LEAD()
  • FIRST_VALUE()
  • LAST_VALUE()
  • NTH_VALUE()

Window functions - 3-year moving average

SQL Code

SELECT
  country,
  year,
  mfg,
  ROUND(AVG(mfg) OVER (
    PARTITION BY country
    ORDER BY year
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
  ),2) AS movavg_3yr
FROM yearly
WHERE country = 'Brazil'
ORDER BY year;

 

Result set

country year mfg movavg_3yr
Brazil 2014 47 47.00
Brazil 2015 48 47.50
Brazil 2016 50 48.33
Brazil 2017 52 50.00
Brazil 2018 54 52.00
Brazil 2019 57 54.33
Brazil 2020 53 54.67
Brazil 2021 55 55.00

Window functions - 3-year moving average

Explanation

  • ORDER BY year ensures chronological sliding window

  • ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

    • For 2014, only 1 row
    • For 2015, only 2 rows
    • For 2016+, full 3-row window

  • Window recalculates for each row individually

  • Note how ROUND wraps the entire () OVER () block.

 

Result set

Value Functions: LAG / LEAD

SQL Code

SELECT
  country,
  year,
  mfg,
  -- lag (previous) in column
  LAG(mfg, 1) OVER (
    PARTITION BY country
    ORDER BY year
  ) AS lag_mfg,
  -- lead (next) in column  
  LEAD(mfg, 1) OVER (
    PARTITION BY country
    ORDER BY year
  ) AS lead_mfg
FROM yearly
WHERE country = 'Brazil'
ORDER BY year;

Brazil 2014 47 NULL 48.0
Brazil 2015 48 47.0 50.0
Brazil 2016 50 48.0 52.0
Brazil 2017 52 50.0 54.0
Brazil 2018 54 52.0 57.0
Brazil 2019 57 54.0 53.0
Brazil 2020 53 57.0 55.0
Brazil 2021 55 53.0 NULL

Value functions: FIRST_VALUE / LAST_VALUE

SQL Code

SELECT
  country,
  year,
  mfg,
  -- First value in the partition (earliest year)
  FIRST_VALUE(mfg) OVER (
    PARTITION BY country
    ORDER BY year
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS first_mfg,
  -- Last value in the partition (latest year)
  LAST_VALUE(mfg) OVER (
    PARTITION BY country
    ORDER BY year
    ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
  ) AS last_mfg
FROM yearly
WHERE country = 'Brazil'
ORDER BY year;

 

Result set

country year mfg first_mfg last_mfg
Brazil 2014 47 47 55
Brazil 2015 48 47 55
Brazil 2016 50 47 55
Brazil 2017 52 47 55
Brazil 2018 54 47 55
Brazil 2019 57 47 55
Brazil 2020 53 47 55
Brazil 2021 55 47 55

Summary

Window functions enable:

  • Rankings
  • Running totals
  • Moving averages
  • Lagged comparisons
  • Period-over-period changes
  • Locate first/last values without subqueries

They are essential for analytics, BI, and modern SQL workloads.
